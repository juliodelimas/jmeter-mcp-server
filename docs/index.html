Background
Contexto

What is MCP, and why does that matter here?

O que é o MCP, e por que isso importa aqui?

The Model Context Protocol (MCP) is an open standard for connecting an AI model to external tools and data sources through a structured, typed interface — instead of the model guessing at shell commands or generating raw text it hopes is correct. Think of it as a common connector: any MCP client (Claude Code, Claude Desktop, and others) can talk to any MCP server, and the server exposes a fixed menu of tools — each with a name, a description, and a strict input/output schema. The model doesn't write JMeter internals; it picks a tool, like add_http_sampler, and passes structured arguments. The server validates them and does the actual work.

O Model Context Protocol (MCP) é um padrão aberto para conectar um modelo de IA a ferramentas e fontes de dados externas por meio de uma interface estruturada e tipada — em vez de o modelo "chutar" comandos de shell ou gerar texto cru na esperança de que esteja correto. Pense nele como um conector universal: qualquer cliente MCP (Claude Code, Claude Desktop, entre outros) consegue conversar com qualquer servidor MCP, e o servidor expõe um menu fixo de ferramentas (tools) — cada uma com nome, descrição e um schema estrito de entrada/saída. O modelo não escreve os detalhes internos do JMeter; ele escolhe uma ferramenta, como add_http_sampler, e passa argumentos estruturados. O servidor valida tudo e faz o trabalho de verdade.

Why a server, not free-form XML
Por que um servidor, e não XML solto

Why not just ask the LLM to write the .jmx itself?

Por que não simplesmente pedir para a LLM escrever o .jmx?

It can — a .jmx is just XML, and any capable model has seen plenty of JMeter test plans. The problem is how it fails: JMeter's format is a hashTree with dozens of fragile, easy-to-misremember details — exact guiclass/testclass pairs, property names that don't match their GUI label, integer bitmasks for assertion match types, strict parent/child pairing with sibling <hashTree> tags. None of it is self-checking. A wrong value still produces valid, loadable XML that just quietly does the wrong thing.

Consegue — um .jmx é só XML, e qualquer modelo competente já viu muitos planos de teste do JMeter. O problema é como ele falha: o formato do JMeter é uma hashTree cheia de detalhes frágeis e fáceis de lembrar errado — pares exatos de guiclass/testclass, nomes de propriedade que não batem com o rótulo na GUI, bitmasks inteiros para os tipos de assertion, pareamento rígido de pai/filho com tags <hashTree> irmãs. Nada disso se auto-verifica. Um valor errado ainda produz um XML válido e carregável — que simplesmente faz a coisa errada, em silêncio.

This isn't hypothetical — it happened building this project. An early version of the If Controller generated a property called useExpression set to true, which reads like "yes, evaluate my condition." The real JMeter source does the opposite: useExpression=true means don't evaluate it as an expression — just check if the string is literally "true". Every non-trivial condition silently, permanently failed. No error, no warning — the child sampler just never ran. It only surfaced by actually executing the generated plan against real JMeter and noticing a sample count of zero.

Isso não é hipotético — aconteceu na construção deste projeto. Uma versão inicial do If Controller gerava uma propriedade chamada useExpression como true, o que parece dizer "sim, avalie minha condição". O código-fonte real do JMeter faz o oposto: useExpression=true significa não avaliar como expressão — apenas checar se a string é literalmente "true". Toda condição não trivial falhava silenciosa e permanentemente. Sem erro, sem aviso — o sampler filho simplesmente nunca rodava. Só veio à tona executando de fato o plano gerado contra um JMeter real e percebendo uma contagem de amostras igual a zero.

That's the whole case for this server in one story: an LLM regenerating XML from memory re-risks that exact mistake on every single request. This server encodes the correct shape once, in a serializer (and a matching parser for the reverse direction) checked against real JMeter source and bundled examples, exercised by 166 automated tests including real JMeter runs — and exposes it as typed tools instead.

Esse é todo o argumento a favor deste servidor, resumido em uma história: uma LLM regerando XML de memória arrisca repetir exatamente esse erro a cada requisição. Este servidor codifica o formato correto uma única vez, em um serializador (e um parser correspondente para o sentido inverso) verificado contra o código-fonte real do JMeter e exemplos reais, coberto por 166 testes automatizados incluindo execuções reais do JMeter — e expõe isso como ferramentas tipadas.

Architecture
Arquitetura

Why stdio, and why that's the safer choice

Por que stdio, e por que isso é mais seguro

MCP servers can talk to their client over different transports. This one deliberately uses stdio: the server is a plain local process, spawned directly by your MCP client (Claude Code, Claude Desktop), and the two talk by writing JSON-RPC messages to each other's stdin/stdout pipes. Nothing listens on a network port. Nothing is reachable from outside your machine.

Servidores MCP podem conversar com o cliente por diferentes transportes. Este usa stdio de propósito: o servidor é um processo local comum, iniciado diretamente pelo seu cliente MCP (Claude Code, Claude Desktop), e os dois trocam mensagens JSON-RPC escrevendo nos pipes stdin/stdout um do outro. Nada fica escutando em uma porta de rede. Nada é alcançável de fora da sua máquina.

✗ A remote HTTP/SSE MCP server

✗ Um servidor MCP remoto via HTTP/SSE

  • Needs an exposed endpoint, TLS, and its own auth/token story
  • Precisa de um endpoint exposto, TLS e sua própria história de autenticação/token
  • Reachable by anyone with the URL and credentials
  • Alcançável por qualquer um com a URL e as credenciais
  • Your target URLs, test plans, and JMeter output travel to a third-party host
  • Suas URLs alvo, planos de teste e saídas do JMeter trafegam até um host de terceiros
  • A compromised server is a compromised network service
  • Um servidor comprometido é um serviço de rede comprometido

✓ This stdio server

✓ Este servidor stdio

  • Only runs when your own MCP client spawns it — no listening socket, ever
  • Só roda quando o seu próprio cliente MCP o inicia — nenhum socket escutando, nunca
  • Not reachable over the network under any circumstance
  • Não é alcançável pela rede em nenhuma circunstância
  • Inherits only your own OS-level user permissions — no separate auth layer to leak
  • Herda apenas as suas próprias permissões de usuário do sistema operacional — nenhuma camada extra de auth para vazar
  • Test plans, target URLs, and results stay on your disk, in your workspace folder
  • Planos de teste, URLs alvo e resultados ficam no seu disco, na sua pasta de workspace
  • Real JMeter runs against real systems stay under your direct, local control
  • As execuções reais do JMeter contra sistemas reais ficam sob seu controle local e direto

For a tool that runs real load against real target systems and reads/writes local files (.jmx, .jtl, CSV data files), minimizing the blast radius matters: stdio means the smallest possible attack surface — a child process that can only be started by something already running on your machine, with no network identity of its own.

Para uma ferramenta que gera carga real contra sistemas alvo reais e lê/escreve arquivos locais (.jmx, .jtl, arquivos CSV), minimizar o raio de impacto importa: stdio significa a menor superfície de ataque possível — um processo filho que só pode ser iniciado por algo que já está rodando na sua máquina, sem identidade de rede própria.

Instalando o servidor

Published on npm as jmeter-mcp-server — no cloning or building required. Any MCP client spawns it the same way: run npx -y jmeter-mcp-server as a stdio server, with JMETER_HOME set in its environment.

Publicado no npm como jmeter-mcp-server — sem precisar clonar ou compilar nada. Qualquer cliente MCP o inicia da mesma forma: rodando npx -y jmeter-mcp-server como um servidor stdio, com JMETER_HOME definido no ambiente.

Claude Code

Claude Code

Via npx — the recommended route, nothing to clone or build:

Via npx — o caminho recomendado, sem nada para clonar ou compilar:

claude mcp add jmeter \
  -e JMETER_HOME=/opt/homebrew/opt/jmeter/libexec \
  -- npx -y jmeter-mcp-server

Adjust the JMETER_HOME path to your own install. The default scope is local (this project only) — add -s user to make it available across every project:

Ajuste o caminho de JMETER_HOME para a sua instalação. O escopo padrão é local (só este projeto) — adicione -s user para deixá-lo disponível em todos os projetos: 

claude mcp add jmeter -s user \
  -e JMETER_HOME=/opt/homebrew/opt/jmeter/libexec \
  -- npx -y jmeter-mcp-server

Confirm it registered and is responding: claude mcp list

Confirme que ele foi registrado e está respondendo: claude mcp list

Working on this repo's own code instead? Point at the built dist/index.js directly: npm install && npm run build, then claude mcp add jmeter -e JMETER_HOME=... -- node /absolute/path/to/dist/index.js.

Está trabalhando no código deste próprio repositório? Aponte direto para o dist/index.js já compilado: npm install && npm run build, e depois claude mcp add jmeter -e JMETER_HOME=... -- node /caminho/absoluto/para/dist/index.js.

Claude Desktop

Claude Desktop

Add this to ~/Library/Application Support/Claude/claude_desktop_config.json:

Adicione isto em ~/Library/Application Support/Claude/claude_desktop_config.json:

{
  "mcpServers": {
    "jmeter": {
      "command": "npx",
      "args": ["-y", "jmeter-mcp-server"],
      "env": {
        "JMETER_HOME": "/opt/homebrew/opt/jmeter/libexec"
      }
    }
  }
}

Unlike a terminal-launched app, Claude Desktop does not inherit environment variables exported in your shell profile (.zshrc, etc.) — only true system-wide ones. Always set JMETER_HOME explicitly in the env block above rather than relying on it already being "set on your machine".

Diferente de um app iniciado pelo terminal, o Claude Desktop não herda variáveis de ambiente exportadas no seu perfil de shell (.zshrc, etc.) — só as realmente globais do sistema. Sempre defina JMETER_HOME explicitamente no bloco env acima, em vez de contar que ela já está "definida na sua máquina".

Outros clientes MCP

Este é um servidor MCP stdio padrão, então qualquer coisa que fale MCP via stdio consegue rodá-lo — Cursor, Windsurf, Cline, Zed e outros normalmente usam o mesmo formato de config do Claude Desktop: um comando, seus args, e um bloco de env, geralmente sob uma chave mcpServers (ou nome parecido) no arquivo de configuração próprio daquele cliente:

Check that client's own docs for the exact config file location and key name — the command/args/env shape above is the part that stays the same everywhere.

Consulte a documentação daquele cliente para o local exato do arquivo de config e o nome da chave — o formato command/args/env acima é a parte que se mantém igual em todo lugar.

find_breaking_point Automatic binary-search capacity finder: ramps thread count up/down on its own, run after run, until it finds the concurrency level that violates your SLA (p95 latency, error %). Localizador automático de capacidade por busca binária: ajusta a quantidade de threads para cima/baixo sozinho, execução após execução, até achar o nível de concorrência que viola o seu SLA (latência p95, % de erro). JMeter has no native "find the limit" feature. Driving this search through raw LLM tool calls costs ~6-8 calls per round across the several rounds a binary search needs. O JMeter não tem um recurso nativo de "achar o limite". Conduzir essa busca via chamadas de ferramenta cruas custaria de 6 a 8 chamadas por rodada, em várias rodadas de busca binária.
detect_bottleneck_class Fits Little's Law / the Universal Scalability Law to collected concurrency vs. throughput vs. latency data, and classifies the bottleneck as contention, coherency, or saturation. Ajusta a Lei de Little / a Universal Scalability Law aos dados coletados de concorrência vs. throughput vs. latência, e classifica o gargalo como contenção, coerência ou saturação. JMeter only outputs raw numbers; re-deriving a queueing-theory curve fit through prose reasoning would mean reimplementing nonlinear regression by hand. O JMeter só entrega números crus; re-derivar um ajuste de curva de teoria de filas via raciocínio em texto significaria reimplementar regressão não linear na mão.
detect_soak_drift Runs linear regression over the latency/error time series of a long-duration soak test to separate normal noise from a real trend (the classic memory-leak signal). Roda regressão linear sobre a série temporal de latência/erro de um soak test longo para separar ruído normal de uma tendência real (o clássico sinal de vazamento de memória). JMeter's graph shows the curve, but doesn't say whether it's a statistically real degradation or just noise. O gráfico do JMeter mostra a curva, mas não diz se é uma degradação estatisticamente real ou só ruído.
compare_execution_reports Statistical diff across N executions (not just two), with a significance test for whether a p95 shift is real or noise. Diff estatístico entre N execuções (não só duas), com teste de significância para saber se uma mudança no p95 é real ou ruído. A ready-made performance regression gate for CI, instead of someone eyeballing two JSON reports and guessing. Um gate de regressão de performance pronto para CI, em vez de alguém olhando dois relatórios JSON e chutando.
isolate_warmup_window Automatically detects where warm-up (JIT, connection pools, cold caches) ends, and recomputes metrics only over the steady-state window. Detecta automaticamente onde o warm-up (JIT, connection pools, caches frios) termina, e recalcula as métricas só sobre a janela de estado estável. Today's overall average is polluted by the first few seconds of a run; JMeter doesn't separate this on its own. Hoje a média geral é poluída pelos primeiros segundos da execução; o JMeter não separa isso sozinho.
classify_error_flakiness Re-runs failed samples with backoff and separates "real system error" from "one-off flake" (network timeout, etc.). Reexecuta amostras que falharam com backoff e separa "erro real do sistema" de "falha isolada" (timeout de rede, etc.). Produces a trustworthy error rate for a CI gate, instead of an errorPct that mixes both kinds together. Produz uma taxa de erro confiável para um gate de CI, em vez de um errorPct que mistura os dois tipos.
orchestrate_distributed_run Runs the same test plan across multiple JMeter injector nodes (master-slave) and merges every node's .jtl into a single aggregated report. Roda o mesmo plano de teste em vários nós injetores JMeter (master-slave) e mescla o .jtl de cada nó em um único relatório agregado. JMeter supports distributed mode, but wiring up remote engines, RMI ports, matching versions, and merging results is entirely manual today. O JMeter suporta modo distribuído, mas configurar engines remotas, portas RMI, versões compatíveis e mesclar resultados hoje é totalmente manual.

Boa parte do JMeter fica de fora de propósito, por enquanto.
